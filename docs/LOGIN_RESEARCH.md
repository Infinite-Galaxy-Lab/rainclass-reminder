2026-11-09。用户要求单手机、无 root；官方账号密码和验证码入口按用户要求暂缓。

用户提供了 SicnuJw 的“绑定川师微生活”截图，含“分享至微信”“复制链接”和回调链接 / code 手动兜底。

学校入口只用研究用回调地址发出 HEAD，未访问截图中的真实会话；雨课堂入口只作匿名 GET，未请求账号授权。
只保留状态码、域名、路径、查询参数名和 scope，不记录 OAuth state、Cookie 或授权码。

上述差异说明截图展示的是另一条授权流程，不能通过给旧确认链接随意添加参数来推定等价。
同一网站在微信中完成授权，也不能证明独立 Android HTTP client 或 WebView 已获得其 Cookie。

## 公众号场景登录补充

官方 `/authorize/login` 的 chunk `68520.67ed8b9b.js`、模块 `91842` 是 `login-qr` 组件。
它消费 `pre-info` 返回的图片与令牌，以同一令牌发起 `POST /api/v3/user/login`，前端超时为 70.2 秒。
返回体 `code === 0` 后再请求 `basic-info`；换码会取消旧等待请求。该端点只用于认证，不属于业务抓取层。

匿名响应确认：`pre-info` 的二维码内容来自 `weixin.qq.com/q/`，图片来自公众号二维码接口；
`app-web-pre-info` 的二维码内容则指向本站 `app-web-qr`。两者也不能与 alpha.8 的微信确认链接混用。
匿名打开前两类内容未取得有效登录页面；这不代表真实微信内的打开结果已经被验证。

官方通用请求封装在响应含 `set-auth` 时缓存该值，随后发送 Bearer 认证。
这是条件处理代码，不能证明该登录接口的成功响应一定带此头，也不能证明服务器没有同时设置 Cookie。
当前 App 走 Cookie 身份校验；在实际成功响应尚未观察前，不新增 Bearer 存储或把两种认证方式视作等价。
`/authorize/callback` 的对应组件处理腾讯会议 `auth_code`，不是公众号登录结果交回本 App 的证据。

本机匿名诊断工具已保存在仓库外，可重复检查以上三个官方入口，只保存状态、固定路径、参数名等元数据。
两项合成隐私回归覆盖场景链接与 OAuth 查询内容，均实际破坏脱敏取得断言红后恢复绿；
未保存真实二维码内容、OAuth state、令牌、Cookie 或授权码。该工具不测试微信接受性，也不获取已登录会话。

## 后续验收

alpha.9 在独立验证包接入公众号场景流程，用于核对真实微信是否接受新链接，
以及同一等待令牌对应的成功响应能否提供 Cookie 并通过身份校验。
这两个条件尚未满足，不能声称已经支持单手机登录。保持认证与只读业务端点分离，
成功仍须通过现有非零身份校验并加密保存；不把分享链接、打开微信或收到任意 code 视作登录成功。

账号登录的未完成改动仍备份在仓库外，本轮不接入账号密码或验证码。
公众号实验只在调试和验证包显示，常规扫码仍是默认方式；移除 alpha.8 已失败的复制确认链接入口。
切换方式或换码时取消旧会话；每次场景请求最长等待 70.2 秒，整个登录最多五分钟。
收到成功响应仍必须取得 sessionid；仅有 set-auth 不转换为 Cookie，也不保存为现有会话。
随后复用非零身份校验、加密存储与登录后立即同步。

真机步骤：登录页点“尝试公众号链接登录” → “复制链接到微信” → “复制公众号链接”，
在微信文件传输助手发送给自己并点开，按页面提示操作后返回。
若仍要求摄像头扫码，则单手机路径失败；若提示未取得应用登录凭据，则需进一步核查官方会话交接。
以上情况均不能仅凭微信确认而标记 App 登录成功。
